## Method

Every engine is driven by an in-process harness that opens the database once,
prepares once, warms up, and then times N executions: `bench_harness.asm` for
CybouDB, `sqlite_harness.c` for SQLite, `duckdb_harness.c` for DuckDB. The DuckDB
harness pulls a streaming result chunk by chunk through the C API and reads the
raw typed vectors, so no result row becomes a Python object and nothing is
timed through Python. Thread count and read-only access are set on the DuckDB
database at open time, one process per configuration.

| Engine | Execution |
| :--- | :--- |
| SQLite 3 | row B-tree, `PRAGMA mmap_size = 2147483648`, `cache_size = -64000` |
| DuckDB 1.5.5 (1T) | vectorized columnar scan, `threads = 1` set at open |
| DuckDB 1.5.5 (8T) | vectorized columnar scan, `threads = 8` set at open |
| CybouDB Scalar | PAX columnar, handwritten x86-64 scalar kernels |
| CybouDB AVX2 | PAX columnar, 64-row 256-bit AVX2 kernels |

Two comparisons, kept apart because they answer different questions:

- **FILTER** - every engine answers the identical aggregate
  `SELECT count(*) FROM events WHERE <predicate>`. Scan, predicate evaluation
  and aggregation, with no result delivery anywhere. CybouDB runs its own
  `COUNT(*)` plan rather than a `SELECT` whose selection mask the harness sink
  population counts.
- **MATERIALIZE** - every engine reads the same projected values for the same
  rows and folds each delivered value into the same tagged FNV-1a hash
  (`TAG_NULL = 0xBF`, `TAG_VALUE = 0x5A`).

Parity is checked, not assumed: the FILTER table compares the `COUNT` value
each engine returns, and the MATERIALIZE table compares checksums bit for bit
across CybouDB AVX2, CybouDB scalar, SQLite and DuckDB-1T. All of them matched.
DuckDB-8T is excluded from the checksum comparison only because a
multi-threaded result is not required to arrive in table order.

## Reading the numbers

**Against SQLite**, nothing changed in kind: 20-140 ns per row for B-tree page
traversal, record header decoding and VDBE dispatch, against 0.4-7.4 ns for
CybouDB. The `no predicate (full)` row is a metadata answer on both sides - CybouDB
resolves an unpredicated `COUNT(*)` from the directory without touching column
pages, and so does SQLite - which is why it reads 1.1x rather than 20x.

**Against DuckDB**, the honest comparison is much closer than the earlier,
broken one suggested, and it splits cleanly:

- *Single-threaded filters*: CybouDB is ahead on 8 of 10 scenarios (geomean 1.43x).
  DuckDB wins `int64 range` (0.37 vs 0.79) and the metadata-only full scan,
  where its block zone maps decide whole 122 880-row blocks from min/max
  without evaluating anything per row. That is a feature CybouDB does not have,
  and it is the next thing to build.
- *Materialization*: CybouDB is ahead by about 4x at every projection width, and
  the gap holds as the projection widens (1.45 / 3.45 / 7.35 ns per row against
  5.55 / 13.71 / 31.27). Reading values straight out of mapped PAX column runs
  costs less than DuckDB's chunk assembly, even though DuckDB reads a tenth as
  many bytes off disk.
- *Multi-threading*: 8 threads buy DuckDB 3-6x on filters (0.09-0.90 ns per
  row), which is where it beats single-core CybouDB outright. On materialization
  they buy nothing at all (31.77 against 31.27) - delivery, not scanning, is
  the bottleneck there. CybouDB is single-threaded throughout; a fair reading is
  that CybouDB's scalar and AVX2 numbers should be compared with DuckDB-1T, and
  that DuckDB-8T marks what parallelism is worth on this machine.

**Compression is not the whole story it appeared to be.** DuckDB moves roughly
a tenth of the bytes (44.3 MB against 422.6 MB) and still loses the
single-threaded filter comparison on most scenarios and every materialization
scenario. What compression and zone maps buy is visible exactly where DuckDB
wins - wide range predicates and full scans - which is a narrower claim than
the earlier run implied.

## Footprint

`cyboudb.exe` is ~100 KB with no dependencies. The DuckDB library is ~37 MB.

## Reproducing

```sh
sh build.sh --bench && sh build.sh --sqlite-bench && sh build.sh --duckdb-bench
python3 benchmarks/run_3way_benchmark.py --rows 10000000
```

The runner finds the DuckDB C API in an installed `duckdb` Python package, or
takes `--duckdb-lib` / `DUCKDB_DLL`. The generated databases live in
`build/benchrun/`.
