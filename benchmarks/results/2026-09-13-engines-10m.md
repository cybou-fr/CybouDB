# Cross-engine comparison, 10,000,000 rows - 2026-09-13

Host: Intel Core Ultra 7 258V (Family 6 Model 189), Windows 11.
Runner: `benchmarks/run_3way_benchmark.py`, commit `d77e35c`.
Raw output: [structured](2026-09-13-engines-10m-structured.txt),
[high entropy](2026-09-13-engines-10m-high-entropy.txt).

Engines: SQLite 3.50.4, DuckDB 1.5.5 (at 1 and 8 threads), CybouDB with zone maps
off and on. Every engine is driven by an in-process harness that opens the
database once, prepares once, warms up, and then times five iterations; five
process-level repeats with rotated execution order, median reported. Nothing is
timed through Python.

**Both datasets are reported, and the honest one is the second.** `structured`
is regular enough that zone maps skip most of the file - useful for showing what
skipping buys, useless as a general claim. `high_entropy` defeats zone maps
almost entirely, and is the number to quote.

Parity is checked rather than assumed: FILTER compares the count each engine
returns, MATERIALIZE compares a tagged FNV-1a checksum over every delivered
value. **Every scenario matched on every engine**, both datasets.

## Summary, high-entropy data

| Comparison | FILTER | MATERIALIZE |
| :--- | ---: | ---: |
| CybouDB vs SQLite | **34.6x** | **22.0x** |
| CybouDB vs DuckDB, 1 thread | **1.94x** | **4.46x** |
| CybouDB vs DuckDB, 8 threads | **0.55x** | **4.34x** |

Read that third row the way it is written: **on filtering, DuckDB with eight
threads is about 1.8x faster than CybouDB**, which is single-threaded and has no
parallel execution at all. Per core CybouDB is ahead; DuckDB has seven more
cores to bring and brings them.

Materialization is the other way round, and it is not close: reading projected
values out of storage and delivering them, CybouDB is ~4.3x faster than DuckDB
*even with eight DuckDB threads*, because that path barely parallelises in
DuckDB - its 8-thread column is within 2% of its 1-thread column.

## FILTER - `SELECT count(*) FROM events WHERE ...`

Scan, predicate evaluation, aggregation. No result delivery on any engine.
Figures are nanoseconds per logical row; lower is better.

### high_entropy

| Scenario | Selected | SQLite | DuckDB 1T | DuckDB 8T | CybouDB |
| :--- | ---: | ---: | ---: | ---: | ---: |
| zone: all NONE | 4,999,223 | 40.60 | 1.47 | 0.33 | **1.15** |
| zone: half NONE/ALL | 5,000,777 | 36.51 | 1.33 | 0.32 | **1.08** |
| zone: all UNKNOWN | 899,644 | 28.00 | 1.33 | 0.26 | **0.73** |
| int32 equality | 1,250,119 | 34.26 | 1.32 | 0.28 | **0.80** |
| int64 range | 5,000,777 | 36.70 | 1.35 | 0.30 | **1.06** |
| float32 range | 4,997,838 | 46.94 | 4.29 | 1.02 | **1.01** |
| bool equality | 5,000,183 | 35.16 | 1.61 | 0.34 | **0.65** |
| two predicates, AND | 112,668 | 28.63 | 2.10 | 0.47 | **1.33** |
| two predicates, OR | 2,037,095 | 43.88 | 8.51 | 1.97 | **1.25** |
| nullable predicate | 3,429,658 | 38.75 | 7.22 | 1.57 | **0.97** |
| nullable IS NOT NULL | 8,000,900 | 35.74 | 4.87 | 1.02 | **0.57** |
| no predicate (full) | 10,000,000 | 0.31 | 0.00 | 0.01 | **0.03** |

Where CybouDB beats even 8-thread DuckDB: `OR` (1.6x), nullable predicates
(1.6x), `IS NOT NULL` (1.8x) - the cases where DuckDB's own single-thread cost
is highest. Where it loses: the simple integer comparisons, by about 3x, which
is roughly the thread count discounted by scaling.

`no predicate (full)` is a metadata answer for DuckDB and near enough for
CybouDB; neither number means anything about scanning.

### structured (zone maps effective)

Zone maps let CybouDB skip whole leaves, so `all NONE`, `half NONE/ALL` and
`int64 range` drop to 0.04n - 28x faster than the same query with zone maps
turned off. This is what the feature buys when data has locality, and it is why
the geomean against SQLite reads 67.5x on this dataset against 34.6x on the
other. It is a property of the data, not of the engine, and quoting the higher
figure without the dataset would be dishonest.

## MATERIALIZE - `SELECT <cols> FROM events WHERE score > 50`

Scan, predicate evaluation, cell reads, and a tagged FNV-1a checksum over every
delivered value. This is where an engine cannot avoid touching the data.

### high_entropy

| Scenario | Selected | SQLite | DuckDB 1T | DuckDB 8T | CybouDB |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 1 column of 7 | 4,901,392 | 58.18 | 8.18 | 7.95 | **2.08** |
| 3 columns of 7 | 4,901,392 | 103.47 | 21.32 | 21.35 | **4.67** |
| 7 columns of 7 | 4,901,392 | 186.82 | 52.60 | 49.55 | **10.02** |
| 3 of 7, half skippable | 5,000,777 | 107.74 | 22.44 | 21.91 | **5.34** |

Cost scales with columns touched on every engine, which is what a columnar
layout is for; CybouDB's constant is the smaller one, and DuckDB's threads do
not help here.

## File size

| Engine | structured | high entropy |
| :--- | ---: | ---: |
| DuckDB | **51.1 MB** | 360.5 MB |
| SQLite | 322.8 MB | 383.8 MB |
| CybouDB | 422.6 MB | **422.6 MB** |

CybouDB writes uncompressed PAX and its file is the same size either way, so on
compressible data DuckDB is **8.3x smaller** and on incompressible data the
three are within 17%. Compression exists in the format
(`CybouDB_FEATURE_COMPRESSION`) but is not in the default profile and does not
yet shrink the file on disk. **This is the clearest thing DuckDB does better**,
and on a laptop-sized dataset it matters more than a 2x scan difference.

## Ingest

Seeding 10M rows through each engine's own fixture path:

| Engine | structured | high entropy |
| :--- | ---: | ---: |
| CybouDB | 9.4s (1,068,632 rows/s) | 9.2s (1,087,417 rows/s) |
| SQLite | 11.4s (878,602 rows/s) | 41.9s (238,729 rows/s) |
| DuckDB | 12.0s (835,826 rows/s) | 51.3s (194,901 rows/s) |

CybouDB's ingest rate is the same on both datasets because it writes the bytes
it is given; the other two slow by 3.7x and 4.3x on incompressible data, which
is what encoding costs when there is nothing to encode.

Treat this as the weakest number here. These are the fixture generators, not
tuned loaders: no engine was given its fastest available path (`COPY`,
`.import`, prepared batch reuse, bulk appenders), and a serious ingest
comparison would have to.

## What this does not measure

Joins, `GROUP BY`, sorting, window functions, strings, dates and everything else
DuckDB and SQLite have and CybouDB does not. CybouDB's SQL surface is a fraction
of either engine's, and a benchmark restricted to what all three can do is
flattering by construction. It measures the scan and projection path, honestly,
and nothing beyond it.

It also measures none of the reason CybouDB exists - a queue, a stream and a
table under one commit. Neither SQLite nor DuckDB has a comparable primitive, so
there is nothing to compare against.

## Reproducing

```sh
build.bat --bench && build.bat --sqlite-bench && build.bat --duckdb-bench
python benchmarks/run_3way_benchmark.py --rows 10000000 --dataset high_entropy
```

`pip install duckdb` supplies both the seeding package and the C API library; set
`DUCKDB_DLL` to point at a copy installed elsewhere.
