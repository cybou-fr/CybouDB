## Why a second dataset

The structured dataset is generated as `category = row % 8`,
`score = row % 100`, `amount = row * 3` and so on. Every column is a short
repeating cycle, which is close to the best case for run-length encoding, bit
packing and per-block min/max metadata - and it is not what real data looks
like. The high-entropy dataset draws every column from an independent
splitmix64 stream of the row index, keeping the same value ranges so the same
predicates keep comparable selectivity, but leaving nothing for a block to
compress or summarise. Both are deterministic functions of the row index, so
all three engines are seeded bit-identically and their materialization
checksums are compared bit for bit; the CybouDB side is generated by the same two
generators reimplemented in `bench_harness.asm`.

## What compression is actually worth

| Engine | structured | high entropy | change |
| :--- | ---: | ---: | ---: |
| DuckDB | 44.3 MB | 360.5 MB | **8.1x larger** |
| SQLite | 322.8 MB | 383.8 MB | 1.2x larger |
| CybouDB (uncompressed) | 422.6 MB | 422.6 MB | unchanged |

DuckDB's tenfold size advantage was mostly an artifact of the synthetic
pattern. On data without internal structure it stores 360.5 MB against CybouDB's
422.6 MB - a 15% difference, not a factor of ten. Any estimate of what
compression would buy CybouDB should be taken from this row, not from the
structured one.

## What changed, and what did not

**DuckDB loses its two structured wins.** On the structured dataset DuckDB beat
single-threaded CybouDB on `int64 range` (0.37 against 0.79 ns/row) because
`amount = row * 3` is monotonic, so a block's min/max answered the predicate.
With random 64-bit amounts the zone map decides nothing and the same scenario
reverses: 1.05 against 0.85 in CybouDB's favour. The only remaining DuckDB win is
the unpredicated `COUNT(*)`, which both engines answer from metadata.

**CybouDB's numbers move less than DuckDB's**, which is what an uncompressed
layout with no block metadata should do: the work per row does not depend on
what the values are. The scalar path slows down noticeably (1.5-4.8 against
0.4-3.0 ns/row) because unpredictable predicate outcomes cost branch
mispredictions; the AVX2 path, being branch-free, barely moves - `bool
equality` is 0.46 against 0.47 ns/row across the two datasets. That is the
clearest single argument in this benchmark for the vector kernels.

**SQLite is 15-25% slower** across the board, mostly from the larger file.

## Consequence for the roadmap

Zone maps remain worth building: they are what let DuckDB answer a scan without
reading it, and they will do the same for CybouDB wherever data has locality -
which real data usually does, since rows tend to arrive in time order. But the
case for compression is weaker than the structured comparison suggested. At 15%
smaller on realistic data, compression buys a fraction of the memory-bandwidth
saving that the 10x figure implied, and it costs a decode step on every scanned
value. It stays on the list, behind zone maps, and its benefit should be
measured on this dataset rather than the structured one.
