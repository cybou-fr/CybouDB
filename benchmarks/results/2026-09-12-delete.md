# DELETE on a large table

Date: 2026-09-12. Windows 11, x86-64, NVMe. `create-large` databases seeded
with the structured `events` dataset (seven fixed-width columns, 448 rows per
leaf across four pages). Every measurement runs against a fresh copy of the
seeded file; `benchmarks/delete_bench.c` times the step that executes an
already bound statement inside an explicit transaction, and times the commit
separately. Reproduce with:

```sh
build.bat --bench && build.bat --delete-bench
python benchmarks/run_delete_benchmark.py --rows 1000000 --repeats 1 --headroom 6
```

## What the two forms cost

`DELETE FROM table` republishes the schema page with its data root, statistics
root and row count back where `CREATE TABLE` left them. It touches two pages
and does not look at the data, so it does not care how large the table is.

`DELETE ... WHERE` rewrites the rows the predicate did not select into a fresh
graph, so its cost follows the survivors, not the rows removed. Deleting
almost everything is cheap; deleting almost nothing is the worst case.

### 1,000,000 rows, 225 MiB file, one repeat

| scenario | deleted | survivors | exec ms | ns/survivor | commit ms | pages staged | x table |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| delete 1% | 10,000 | 990,000 | 177 | 178 | 678 | 43,965 | 4.76 |
| delete 10% | 100,000 | 900,000 | 155 | 172 | 600 | 39,922 | 4.32 |
| delete 50% | 500,000 | 500,000 | 92 | 184 | 574 | 21,993 | 2.38 |
| delete 90% | 900,000 | 100,000 | 25 | 248 | 661 | 4,098 | 0.44 |
| delete 99% | 990,000 | 10,000 | 11 | 1,096 | 667 | 378 | 0.04 |
| delete all, predicated | 1,000,000 | 0 | 1.3 | - | 730 | 2 | 0.00 |
| delete all, unqualified | 1,000,000 | 0 | 0.6 | - | 638 | 2 | 0.00 |
| delete none | 0 | 1,000,000 | 0.7 | - | 1,090 | 0 | 0.00 |

Cost per surviving row is flat at about 180 ns from ten thousand survivors to
very nearly a million, so the rewrite is linear in what it carries over. It
was not: see below.

`delete none` is a full scan that stages nothing: 0.5 ms over a million rows,
which is the zone-map evaluator skipping every leaf. A predicate that matches
everything is recognised and takes the truncation path, which is why it lands
next to the unqualified form rather than next to `delete 1%`.

The commit is flat at roughly 600-1,100 ms whatever the statement staged. It
is a flush of the mapping, so it scales with the file rather than with the
work, and now that the rewrite is linear the commit is the larger number in
every row of the table.

## It was quadratic, and the reason was not the rewrite

The first run of this benchmark measured 124,452 ms for `delete 1%` at a
million rows rather than 177. Cost per surviving row was not constant: 1.4 us
at 10,000 survivors, 6.4 us at 50,000, 11.3 us at 90,000, and 126 us at
990,000. What follows is how that was tracked down, because the shape of the
search is more reusable than the answer.

The cause is not in the DELETE path. The same shape appears in a plain INSERT
that stages the same number of rows in one transaction, with no DELETE
anywhere:

| rows appended in one transaction | ms |
| ---: | ---: |
| 30,000 | 190 |
| 60,000 | 512 |
| 90,000 | 1,018 |

Three measurements pin down what it depends on:

* **Not the table's size.** Appending 30,000 rows in one transaction costs
  190 ms against an empty table and 212 ms against one that already holds
  60,000 committed rows.
* **The open transaction's staged state.** The same 90,000 rows cost 1,004 ms
  in one transaction and 293 ms in nine, commits included.
* **Not the zone maps.** A database created without them measures the same,
  at 200,000 rows, to within noise (5,110 ms against 5,026 ms for the 1%
  case).

So something on the append path cost time proportional to what the
transaction had already staged, and every chunk of the rewrite paid it again.
A predicated DELETE cannot avoid staging the whole rewrite - that is what
makes it atomic and what lets ROLLBACK discard it - so it inherited the
behaviour in full. The bulk seeder in `bench_harness.asm` sidestepped it by
committing every chunk, which is why seeding a million rows took 0.3 s while
rewriting 990,000 of them took 124 s.

## Where the per-append cost is

`benchmarks/append_probe.c` appends fixed chunks into one uncommitted
transaction and, after each one, times what `db_pax_insert` does before it
touches any data. One call accounts for the growth:

| chunk | append us | db_catalog_get ns | db_bitmap_headroom ns | pages staged |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 35.6 | 9,600 | 0 | 5 |
| 20 | 187.5 | 45,000 | 0 | 123 |
| 60 | 325.0 | 109,700 | 100 | 358 |
| 100 | 659.5 | 173,900 | 0 | 600 |
| 140 | 747.7 | 244,800 | 0 | 874 |
| 199 | 1,091.3 | 338,200 | 0 | 1,281 |

`db_catalog_get` tracked the pages the transaction had staged, near enough
exactly - 123 pages cost 45 us, 1,281 pages cost 338 us. `db_bitmap_headroom`,
timed beside it as a control, stays at the clock's resolution throughout, so
neither the loop nor the timer is what is growing.

Committing every twenty chunks holds staged pages at about seven, and with it
`db_catalog_get` stays at 16-26 us and the append itself at about 170 us
rather than climbing to 1,091 us.

The work is checksum work. Forcing the scalar CRC-32C - a knob that changes
nothing else - takes `db_catalog_get` at chunk 199 from 372 us to 29,922 us,
a factor of eighty, which is the hardware-to-scalar ratio for that routine.

The path is: `db_pax_insert` resolves the table's schema through
`db_catalog_get`, which calls `current_valid`, which builds a synthetic
superblock standing at the *staged* generation and hands it to
`db_catalog_validate`. That walks the whole typed graph - the directory, every
schema page, and through `db_pax_validate` and `db_zone_validate` the table's
own pages - and `db_bitmap_deep` returns true for exactly those pages whose
generation matches the one in that synthetic superblock, which is every page
this transaction has staged. So each append re-verifies everything the
previous appends staged. The publication that follows it,
`catalog_publish_data`, calls `db_catalog_get` a second time, so the walk
happens twice per append.

That explains every observation: it grows with staged state rather than table
size, because committed pages carry older generations and are skipped; it is
unaffected by the zone maps, because they are one more thing being validated
rather than the reason; and it disappears when the work is split across
commits, because committing is what makes staged pages old.

## The fix

The read side already had the answer. `db_pax_scan_open_bound` exists so that
a bound query does not revalidate the catalog on every batch; the append path
had no equivalent, and it is the same problem. A writer that staged those
pages itself, microseconds ago, in its own address space, learns nothing from
checksumming them again - and it was not the only thing checking. `db_commit`
already walks the typed graph before publishing, through `db_bitmap_validate`,
so the boundary that matters was covered either way.

Two changes, both saying "this writer has already proved this graph":

* `current_valid` records that the walk succeeded and skips it for the rest of
  the transaction. The flag is cleared wherever staged state is published or
  discarded, and never set for a reader.
* `db_pax_check_new`, which the publication calls to check the new data root,
  falls back to verifying that root's header - magic, page id, owner,
  generation - instead of walking the table. `cyboudb check` and any open
  asking for exhaustive verification still take the full path.

`tests/commit_guard_test.c` pins what is now the only check between a staged
page and a durable one: it stages a mutation, damages a page the transaction
staged - a catalog root, a leaf, and a row count resealed so its checksum
still matches - and requires the commit to refuse each time and the database
to stay usable afterwards.

Measured with the same probe, one transaction, hardware CRC:

| chunk | append us before | append us after | pages staged |
| ---: | ---: | ---: | ---: |
| 0 | 35.6 | 32.8 | 5 |
| 60 | 325.0 | 14.3 | 358 |
| 120 | 639.5 | 16.2 | 737 |
| 199 | 1,091.3 | 16.5 | 1,281 |

Flat. The same 90,000 rows that took 1,004 ms in one transaction and 293 ms in
nine now take 153 ms in one and 180 ms in nine - the single transaction is
faster, which is the right way round, since it commits once.

For DELETE at a million rows: 124,452 ms to 177 ms for the 1% case, and the
cost per surviving row is constant across every selectivity.

## Page amplification

The rewrite stages up to 4.8x the pages the table itself occupies. Part of
that is the copy of the survivors, which is unavoidable in an append-only
COW store; the rest is per-chunk churn, because every appended chunk copies
the tail leaf run, the directory, the schema page and the catalog root. The
chunk is 279 rows for this schema, bounded by the executor's frame scratch, so
a leaf of 448 rows is written across two chunks and copied twice.

A file must therefore have room for roughly five times the table before a
predicated DELETE of a small fraction will fit. With less, the allocator falls
back to reclaiming retired pages, and with much less the statement fails with
`E_FULL` and stages nothing, which is the correct outcome but not an obvious
one to a caller sizing a database.

## Measurement conditions

Single run at 1,000,000 rows, median of three at 100,000. The numbers above
are one machine's, on a warm page cache, and the commit figures in particular
will differ on other storage. Nothing here is a comparison against another
engine: no other engine implements DELETE the way this one currently does, so
the useful comparison is against the next version of this one.
