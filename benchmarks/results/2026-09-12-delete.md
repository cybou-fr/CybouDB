# DELETE on a large table

Date: 2026-09-12. Windows 11, x86-64, NVMe. `create-large` databases seeded
with the structured `events` dataset (seven fixed-width columns, 448 rows per
leaf across four pages). Every measurement runs against a fresh copy of the
seeded file; `benchmarks/delete_bench.c` times the step that executes an
already bound statement inside an explicit transaction, and times the commit
separately. Reproduce with:

```sh
build.bat --bench && build.bat --delete-bench
python benchmarks/run_delete_benchmark.py --rows 1000000 --repeats 1 --headroom 6
```

## What the two forms cost

`DELETE FROM table` republishes the schema page with its data root, statistics
root and row count back where `CREATE TABLE` left them. It touches two pages
and does not look at the data, so it does not care how large the table is.

`DELETE ... WHERE` rewrites the rows the predicate did not select into a fresh
graph, so its cost follows the survivors, not the rows removed. Deleting
almost everything is cheap; deleting almost nothing is the worst case.

### 1,000,000 rows, 225 MiB file, one repeat

| scenario | deleted | survivors | exec ms | ns/survivor | commit ms | pages staged | x table |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| delete 1% | 10,000 | 990,000 | 124,452 | 125,709 | 435 | 43,965 | 4.76 |
| delete 10% | 100,000 | 900,000 | 104,706 | 116,340 | 381 | 39,922 | 4.32 |
| delete 50% | 500,000 | 500,000 | 33,211 | 66,422 | 357 | 21,993 | 2.38 |
| delete 90% | 900,000 | 100,000 | 1,316 | 13,161 | 502 | 4,098 | 0.44 |
| delete 99% | 990,000 | 10,000 | 23 | 2,315 | 497 | 378 | 0.04 |
| delete all, predicated | 1,000,000 | 0 | 2.8 | - | 642 | 2 | 0.00 |
| delete all, unqualified | 1,000,000 | 0 | 1.3 | - | 992 | 2 | 0.00 |
| delete none | 0 | 1,000,000 | 0.5 | - | 533 | 0 | 0.00 |

`delete none` is a full scan that stages nothing: 0.5 ms over a million rows,
which is the zone-map evaluator skipping every leaf. A predicate that matches
everything is recognised and takes the truncation path, which is why it lands
next to the unqualified form rather than next to `delete 1%`.

The commit is flat at roughly 400-1000 ms whatever the statement staged. It is
a flush of the mapping, so it scales with the file rather than with the work,
and at this file size it dominates everything except the large rewrites.

## The rewrite is quadratic, and that is not the rewrite's doing

Cost per surviving row is not constant. It rises with the number of survivors:
1.4 us at 10,000, 6.4 us at 50,000, 11.3 us at 90,000, 12.3 us at 99,000, and
126 us at 990,000. The total is therefore quadratic, which is what turns a
million-row table into two minutes.

The cause is not in the DELETE path. The same shape appears in a plain INSERT
that stages the same number of rows in one transaction, with no DELETE
anywhere:

| rows appended in one transaction | ms |
| ---: | ---: |
| 30,000 | 190 |
| 60,000 | 512 |
| 90,000 | 1,018 |

Three measurements pin down what it depends on:

* **Not the table's size.** Appending 30,000 rows in one transaction costs
  190 ms against an empty table and 212 ms against one that already holds
  60,000 committed rows.
* **The open transaction's staged state.** The same 90,000 rows cost 1,004 ms
  in one transaction and 293 ms in nine, commits included.
* **Not the zone maps.** A database created without them measures the same,
  at 200,000 rows, to within noise (5,110 ms against 5,026 ms for the 1%
  case).

So something on the append path costs time proportional to what the
transaction has already staged, and every chunk of the rewrite pays it again.
A predicated DELETE cannot avoid staging the whole rewrite - that is what
makes it atomic and what lets ROLLBACK discard it - so it inherits the
behaviour in full. The bulk seeder in `bench_harness.asm` avoids it by
committing every chunk, which is why seeding a million rows takes 0.3 s while
rewriting 990,000 of them takes 124 s.

Finding where that per-append cost comes from is the prerequisite for any
DELETE performance work: halving the rewrite's constant factor is worth
nothing against a quadratic term. It is worth fixing on its own account, since
it slows every large single-transaction INSERT by the same rule.

## Page amplification

The rewrite stages up to 4.8x the pages the table itself occupies. Part of
that is the copy of the survivors, which is unavoidable in an append-only
COW store; the rest is per-chunk churn, because every appended chunk copies
the tail leaf run, the directory, the schema page and the catalog root. The
chunk is 279 rows for this schema, bounded by the executor's frame scratch, so
a leaf of 448 rows is written across two chunks and copied twice.

A file must therefore have room for roughly five times the table before a
predicated DELETE of a small fraction will fit. With less, the allocator falls
back to reclaiming retired pages, and with much less the statement fails with
`E_FULL` and stages nothing, which is the correct outcome but not an obvious
one to a caller sizing a database.

## Measurement conditions

Single run at 1,000,000 rows, median of three at 100,000. The numbers above
are one machine's, on a warm page cache, and the commit figures in particular
will differ on other storage. Nothing here is a comparison against another
engine: no other engine implements DELETE the way this one currently does, so
the useful comparison is against the next version of this one.
