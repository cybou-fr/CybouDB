# What the durability barrier scales with

**Date:** 2026-09-14
**Engine:** `065b6db`
**Harness:** `benchmarks/flush_probe.c`, `sh build.sh --flush-probe` /
`build.bat --flush-probe`
**Machines:** Windows 11 on NTFS (native), WSL2 Linux on an ext4 virtual disk.

The `preview.2` baseline left one thing open and made it the larger one: the
flush is about 99% of a commit and gets more expensive as a database holds
more. This asks what causes that. The deliverable is a measurement and a cause,
not a fix — whether a fix belongs in `0.6` is a decision this is meant to make.

---

## The answer, first

**The flushed range is not the cause.** At a constant 13-page range, sync time
grows more than tenfold with what the database holds:

| depth | flush pages | sync us | commit us |
| ----: | ----------: | ------: | --------: |
| 0 | 13.00 | 564.6 | 639.0 |
| 2000 | 13.00 | 1595.8 | 1673.7 |
| 10000 | 13.00 | 5983.1 | 6103.2 |

Windows, NTFS, 60,000-page file, 150 measured commits at each depth. The file
is the same length throughout — `cyboudb_create` allocates it up front — so
this is not the file growing either. It is how much of the file has been
written.

**And it survives a close and reopen**, which rules out the obvious second
explanation:

| mode | flush pages | sync us | on disk |
| :--- | ----------: | ------: | ------: |
| empty | 13.00 | 533.3 | 234 MB |
| fresh, depth 10000 | 13.00 | 6062.7 | 234 MB |
| reopen, depth 10000 | 13.00 | 5921.6 | 234 MB |
| drained, depth 10000 | 59998.50 | 9193.1 | 234 MB |

`reopen` closes the database after filling it and opens it again before
measuring. Closing unmaps and flushes, so anything still dirty in the mapping
is gone by then — and the cost does not move. Whatever the filesystem is
charging for is a property of the file once it has been written, not of state
the engine is still holding.

---

## The thing found on the way, which is the engine's own doing

`drained` in that table has a flushed range of **59,998 pages** where every
other row has 13. The engine is asking the kernel to flush the whole file for
a change of a few pages.

The range a commit flushes is a hull — `DB_DIRTY_LO..DB_DIRTY_HI`, widened by
`mark_dirty` to cover the lowest and highest page a transaction touched. Once
the allocator starts reusing retired pages it serves them from the bottom of
the file, while the transaction still writes near the high-water, and the hull
becomes everything in between.

Measured directly, on an 8,000-page file with no draining at all:

| messages written | high-water | dirty hull | pages |
| ---------------: | ---------: | :--------- | ----: |
| 1500 | 6007 | `[6007, 6011)` | 4 |
| 2000 | 8000 | `[5, 8001)` | 7996 |

And the same thing in flushed pages per commit:

| messages written | flush pages per commit |
| ---------------: | ---------------------: |
| 1200 | 8.50 |
| 1500 | 8.50 |
| 1800 | 8.50 |
| 2000 | **7999.00** |
| 2200 | **7999.00** |

**The trigger is the file reaching its high-water capacity, not a queue
emptying.** The first sighting was a queue filled to 10,000 and drained, which
made it look like draining was the cause; draining 2,000, 5,000 and 9,000 of
10,000 in a 60,000-page file leaves the range at 13, because none of those
exhaust the file. Draining all 10,000 does exhaust it, and the range goes to
59,998. In an 8,000-page file the same thing happens at 2,000 messages with no
draining at all.

`db_bitmap_recount` restarts the reuse sweep at `CybouDB_MIN_PAGES` after every
commit, so the reused page is always near the bottom.

### Does the wide range cost anything?

On Linux, no, twice over: growing a file from 60,000 to 4,000,000 pages takes
the flushed range from 12 to 379 pages and leaves sync flat, and the hull
explosion from 8.50 to 7,999 pages leaves it flat as well —

| messages | flush pages | sync us |
| -------: | ----------: | ------: |
| 1800 | 8.50 | 7967.3 |
| 2000 | 7999.00 | 7637.7 |
| 2200 | 7999.00 | 4596.7 |

On Windows the `drained` row costs 9,193 us against 6,063 for the same
database with a 13-page range — but those two also differ in how much was
written, so that is suggestive and not established. What can be said is that
asking for 234 MB of range to publish a few pages is not free in principle, and
is indefensible in any case.

---

## What this does not answer

The environment matters more than expected, and one of them is unusable for
this. The same measurements on the WSL2 virtual disk gave **7.4 ms for a 32 MB
file and 6.7 ms for a 161 MB one**, and a `reopen` anomaly — 16.3 ms against
6.7 for `fresh` — that does not reproduce natively. Every timing conclusion
here is from the Windows/NTFS runs for that reason.

What the filesystem is actually charging for once a file has been written all
over — extent count, valid data length, metadata — is not established here. It
would need instrumentation below the engine.

---

## What follows

Two separate things, and they should not be confused with each other.

1. **The hull was the engine's bug, and it is fixed.** Flushing 234 MB of
   range to publish 13 pages is wrong whatever it costs, and
   `docs/COMMIT_VALIDATION.md` already said why a hull is the wrong shape: it
   claims a page may have been written when it was not. A transaction's writes
   are now kept as a small set of contiguous runs beside the hull, and a commit
   flushes the runs — every one but the last without a barrier, then the last
   through `sync_pages`, so there is still exactly one barrier. The hull stays
   as the fallback when a transaction is more scattered than the set can hold:
   it covers the runs, so falling back flushes more than needed and never less.

   Measured on the same 8,000-page file, at the depth where the hull used to
   explode:

   | messages | flush pages, before | after |
   | -------: | ------------------: | ----: |
   | 1800 | 8.50 | 8.50 |
   | 2000 | **7999.00** | **9.50** |
   | 2300 | **7999.00** | **9.50** |

2. **The dominant term is not the engine's to fix by flushing less.** At a
   constant 13-page range the cost still grows tenfold with how much of the
   file has been written, and survives a reopen. Reducing it means writing less
   of the file, which is a different and much larger question than the barrier.

So: nothing in `0.6` should promise to make a deep queue commit fast. The hull
is worth a small, well-tested change; the rest is a measurement result, which
is what this was for.

## Reproducing

```sh
sh build.sh --flush-probe
./build/flush_probe <path> <pages> <depth> <rounds> <fresh|reopen|drained|empty>
```

Run it on the filesystem being measured, and not on a virtual disk if the
numbers are meant to mean anything.
