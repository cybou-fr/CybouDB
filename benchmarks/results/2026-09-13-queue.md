# A durable work queue: CybouDB against SQLite - 2026-09-13

Host: Intel Core Ultra 7 258V, Windows 11, NVMe. SQLite 3.50.4.
Runner: `benchmarks/run_queue_benchmark.py`, harness `benchmarks/queue_bench.c`.
Raw output: [2026-09-13-queue-matrix.txt](2026-09-13-queue-matrix.txt).

CybouDB has a queue in the storage engine. SQLite does not, so a service that
needs one builds it from a table - which is how most durable job queues are
actually written. SQLite takes a message with

```sql
DELETE FROM jobs WHERE id = (SELECT id FROM jobs ORDER BY id LIMIT 1)
RETURNING payload
```

one statement, atomic, which is what a careful person writes on a modern
SQLite. Both engines prepare once and step/reset in the loop, so neither pays
SQL parsing per message.

**Three questions are measured separately, because one number answers none of
them:**

| | what it asks |
| :--- | :--- |
| **latency** | what does one durable message cost |
| **throughput** | what does it cost when a consumer batches |
| **scaling** | does a commit get more expensive as the queue fills |

Durability decides the first, so SQLite is measured in three configurations,
each labelled with what it promises. CybouDB has no such knob: it flushes the
data pages and then the publication, every commit, always.

## The short version

**CybouDB has an expensive durable commit and amortises it well.** One message
per transaction costs 1,120 us; a hundred per transaction costs 20.75 us each.
That is a 54x difference, and it is the most important thing to know about
writing against this engine.

**SQLite in WAL mode is faster at every batch size**, because its commit is an
append and one flush against CybouDB's two. The gap narrows sharply for
`DEQUEUE` under batching - 0.17x at one message per transaction, 0.70x at a
hundred - and does not narrow for `ENQUEUE`.

**Against SQLite's own default durability** (rollback journal, `synchronous =
FULL`) CybouDB is ahead on enqueue and dequeue at small batches, and level with
it at a hundred.

## Latency and throughput

Microseconds per message; lower is better.

| SQLite WAL+NORMAL *(weaker)* | 14.31 | 1.48 | 0.50 |

Taking a message is where batching helps CybouDB most: against WAL+FULL the gap

### WORKER - take a job and write its result, one transaction

| Engine | 1 per txn | 10 per txn | 100 per txn |
| :--- | ---: | ---: | ---: |
| **CybouDB** | 2777.08 | 334.41 | 67.31 |
| SQLite rollback+FULL | 1968.29 | 222.91 | 38.13 |
| SQLite WAL+FULL | **351.58** | **51.62** | **19.48** |
| SQLite WAL+NORMAL *(weaker)* | 41.20 | 17.09 | 14.37 |

This is the one CybouDB loses at every batch size, including against SQLite's
default. Two mutations in one transaction is two objects to prove at commit,
and the proof is what is expensive here.

## Scaling - the part that is a defect

Enqueue at one message per transaction, as the queue gets deeper:

| Engine | depth 500 | depth 1,000 | depth 2,000 |
| :--- | ---: | ---: | ---: |
| **CybouDB** | 811.73 | 991.38 | 1193.29 |
| SQLite rollback+FULL | 2163.71 | 2164.00 | 2215.16 |
| SQLite WAL+FULL | 339.39 | 324.25 | 329.79 |
| SQLite WAL+NORMAL | 15.40 | 17.33 | 16.62 |

Every SQLite row is flat. CybouDB's is not: step 1 of its commit proves the
staged graph by walking what the generation reaches, and a deeper queue is a
bigger walk. O(depth) per commit, O(depth^2) to fill a queue.

This is a **known performance limitation of the preview**, not a correctness
one. Nothing published is wrong, crash safety is unaffected, corruption
detection is unaffected, and the workaround is the batching above plus keeping
retained depth bounded with `DEQUEUE` or `TRIM`.

### An experiment that failed, kept because it is useful

The obvious suspect was the checksum: the walk re-sums every 4 KiB segment on
every commit, including pages an older generation sealed and which
copy-on-write guarantees have not changed. Every other subsystem asks
`db_bitmap_deep` whether a page is worth re-summing - fresh generation, or
`cyboudb check` - and the queue is the one that does not. Making it follow the
rule looked like a cheap, architecturally pre-approved win.

It bought nothing: 746, 848 and 1092 us at the three depths, against 764, 830
and 1092 before. So the counters were asked instead of the clock:

| Depth | segments visited per commit | catalog pages per commit |
| ---: | ---: | ---: |
| 500 | 4.5 | 2.0 |
| 1,000 | 8.6 | 2.0 |
| 2,000 | 16.6 | 2.0 |

The cost is the **visit**, not the sum - page id, allocation-map membership,
magic, version, owner, start position, about thirty scattered page touches per
message in an 800 MB file. The catalog work beside it is constant.

It also had a price. `tests/queue_page_test.c` damages one byte of a slot
inside a segment an earlier generation wrote and requires the commit to refuse
it; a skipped checksum does not refuse it. Giving up something a commit
currently catches, for nothing a clock can see, is not a trade - so the change
was reverted, and the measurement lives in the comment in
`db_queue_segments_valid` where the next person to have the same good idea will
find it.

Gating the structural checks the same way would not be sound either:
`db_bitmap_candidate_payload` asks whether the page is still payload in *this*
candidate map, and the map changes every commit. What is needed is a commit
that knows a directory's entries have not changed since it last proved them -
real incremental validation, a change to the invariant that keeps an incoherent
file from being published. It is the first engine work after this preview.

## What this does not measure, and it is the whole point

The reason to want a queue inside the database is not throughput:

```sql
BEGIN;
DEQUEUE FROM inbox;                     -- take the work
INSERT INTO jobs VALUES (1, 'done');    -- record the result
APPEND TO audit VALUES ('job 1 done');  -- and say so
COMMIT;
```

SQLite can do the first two - a table-based queue lives in the same database as
the results, so a `DELETE` and an `INSERT` commit together, which is exactly why
the pattern is popular. What it cannot do is the third, because it has no
stream, and it cannot do any of it against a *separate* broker, which is the
case the outbox pattern exists for.

So the honest claim is narrow. CybouDB's queue is not faster than a SQLite
table used as a queue, and against WAL it is slower at every batch size. What
it offers is a queue, a stream and a table under one commit, with the queue's
semantics in the engine rather than in each application's SQL. A project that
needs throughput and not that should use SQLite in WAL mode today.
