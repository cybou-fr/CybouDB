# A durable work queue: CybouDB against SQLite - 2026-09-13

Host: Intel Core Ultra 7 258V, Windows 11, NVMe. SQLite 3.50.4.
Runner: `benchmarks/run_queue_benchmark.py`, harness `benchmarks/queue_bench.c`.
Raw output: [2026-09-13-queue-2k.txt](2026-09-13-queue-2k.txt).

**CybouDB loses this benchmark.** It is published because it is true, and
because the conclusion it supports is a real one: the queue primitive is worth
having for what it *guarantees*, not for how fast it is.

## What is compared

CybouDB has a queue in the storage engine. SQLite does not, so a service that
needs one builds it from a table - which is how most durable job queues are
actually written. SQLite takes a message with

```sql
DELETE FROM jobs WHERE id = (SELECT id FROM jobs ORDER BY id LIMIT 1)
RETURNING payload
```

one statement, atomic, which is what a careful person writes on a modern
SQLite. Both engines prepare once and step/reset in the loop, so neither pays
SQL parsing per message.

Durability decides this benchmark, because at one transaction per message the
flush dominates everything else. CybouDB flushes twice per commit - the data
pages, then the publication - and **has no knob to turn that off**. SQLite is
measured in three configurations, each labelled with what it promises.

## Results - 2,000 messages, 32-byte payload, microseconds per message

| Engine | enqueue | dequeue | worker | 100 per txn |
| :--- | ---: | ---: | ---: | ---: |
| **CybouDB** | 1102 | 1776 | 3023 | 21.9 |
| SQLite rollback + FULL *(SQLite's default)* | 2204 | 2373 | 2266 | 19.3 |
| SQLite WAL + FULL *(same durability class)* | **323** | **348** | **365** | **3.8** |
| SQLite WAL + NORMAL *(weaker: may lose recent commits)* | 18.2 | 28.6 | 39.5 | 0.5 |

CybouDB against each, above 1.00 meaning CybouDB is faster:

| | enqueue | dequeue | worker | 100 per txn |
| :--- | ---: | ---: | ---: | ---: |
| vs rollback + FULL | **2.00x** | **1.34x** | 0.75x | 0.88x |
| vs WAL + FULL | 0.29x | 0.20x | 0.12x | 0.17x |
| vs WAL + NORMAL | 0.02x | 0.02x | 0.01x | 0.02x |

CybouDB beats SQLite's *default* configuration on enqueue and dequeue. Against
**WAL at the same durability** it is 3.4x to 8.3x slower, and against the
WAL+NORMAL configuration most production code actually runs, 50x to 100x
slower.

## Why, and the part that is a design problem

Two separate causes, and only the first is a fair cost of the guarantee.

**One: two flushes against one.** CybouDB's commit protocol flushes the data
pages and then the publication. SQLite in WAL mode appends to the log and
flushes once. On this machine a flush is about 300 us, which is very nearly the
whole of SQLite's WAL+FULL number - so roughly 2x of the gap is CybouDB buying
the same durability with twice the syncs. A WAL would close that, and CybouDB
does not have one.

**Two: commit cost grows with queue depth.** This one is not a trade-off, it is
a scaling problem. Per-message cost, enqueue only:

| Messages in the queue | CybouDB | SQLite WAL+FULL |
| ---: | ---: | ---: |
| 500 | 764 us | 297 us |
| 1,000 | 830 us | 337 us |
| 2,000 | 1092 us | 326 us |

SQLite is flat. CybouDB is not, because step 1 of its commit proves the staged
graph by walking what the generation reaches, and a deeper queue is a bigger
graph. That is O(depth) per commit and O(depth^2) to fill a queue. It is the
same validation that makes the engine refuse to publish an incoherent file -
which is a property worth having - but it should be proportional to the change,
the way `db_catalog_page` was already made proportional for INSERT. Recorded in
ROADMAP.md as the first thing to fix after the preview.

## What this does not measure, and it is the whole point

The reason to want a queue inside the database is not throughput. It is that
this is one transaction:

```sql
BEGIN;
DEQUEUE FROM inbox;                     -- take the work
INSERT INTO jobs VALUES (1, 'done');    -- record the result
APPEND TO audit VALUES ('job 1 done');  -- and say so
COMMIT;
```

SQLite can do the first two - a table-based queue is in the same database as
the results, so a `DELETE` and an `INSERT` commit together, and that is exactly
why the pattern is popular. What it cannot do is the third, because it has no
stream, and it cannot do any of it against a *separate* broker, which is the
case the outbox pattern exists for.

So the honest claim after this benchmark is narrow: CybouDB's queue is not
faster than a SQLite table used as a queue, and against WAL it is substantially
slower. What it offers is a queue, a stream and a table under one commit, with
the queue's semantics in the engine rather than in each application's SQL. If a
project needs throughput and not that, SQLite in WAL mode is the better answer
today, and this file says so.
